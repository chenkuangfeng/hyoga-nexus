# Technical Design: P0 架构与项目结构基线收尾

## 1. 设计原则

P0 只提供可安装、可启动、可识别状态的项目骨架。现有架构和目录设计作为目标边界，但不据此推断目录内业务能力已经实现。API、Web、worker 均保持薄入口；P1 平台逻辑仍留待独立 OpenSpec 变更审批和实施。

## 2. 当前基线盘点

静态读取仓库可见以下现状：

- 根目录 README 已说明 `uv sync --locked --extra dev`、API、Web 和 worker 的启动方式及当前能力边界。
- `apps/api/src/nexus_api/main.py` 已提供 `/api/v1/health` 和 `/api/v1/capabilities`；能力项返回 `planned`。
- `apps/web` 已使用 Vue 3、TypeScript、Vite 和 Element Plus；`OverviewView.vue` 读取能力目录并呈现加载/API 错误状态。
- Worker 入口仅打印尚无队列/调度配置的说明。
- 软件测试目录已有健康与能力占位状态的测试，但本设计阶段不执行测试。
- packages 下多数是空模块骨架；当前 docs 已明确尚无 Agent 执行、权限、知识库、渠道和观澜数据业务能力。

以上基线已完成运行验收：锁定安装成功；pytest 2 项通过；API 启动后健康与能力端点均返回 200；worker 输出未配置调度/队列的占位说明并正常退出；在 Node 22.23.4 下 `npm ci` 和生产构建成功。构建输出有主 JS chunk 超过 500 kB 的提示。

## 3. 实施核对结果

1. 已以 REQ-01 至 REQ-07 为检查清单核对并运行验收现有实现。
2. 未发现需要修复的实现差异；未移动目标架构目录，也未添加业务 CRUD 或服务实现。
3. 已同步 architecture/roadmap 中 P0 基线状态，并保留现有功能边界说明。
4. 锁定安装、测试、API/worker 启动和前端生产构建已执行并通过；未进行交互式浏览器检查。
5. P1 数据、授权、迁移和事件语义仍由独立 OpenSpec 变更管理。

## 4. 接口与依赖

- 保持现有健康和能力目录 API 的响应语义；如需调整，应保持端点版本兼容。
- 不引入数据库、ORM、队列、Embedding、Runtime SDK 或领域数据提供方依赖。
- Web 继续通过 Vite `/api` 代理访问 API；P0 不建立认证和生产反向代理。
- Worker 仍为明确的空闲入口，不宣称具备调度、消费、重试或取消能力。

## 5. 风险与非目标

- 静态代码存在不等于可运行验证；实际启动、安装和浏览器验收需要单独执行并报告环境限制。
- 当前 API 健康检查只表示 HTTP 应用存活，不是依赖项就绪检查。
- 本变更不解决根项目对 workspace 空包的打包/安装策略争议；若实现确有阻塞，再以最小且可追溯方式处理，不为预留模块预装第三方依赖。
