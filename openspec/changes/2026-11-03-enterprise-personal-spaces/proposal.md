# 个人空间与企业空间：空间类型、企业账号与组织维护

## 状态

已确认（2026-11-03）。用户确认了个人与企业两类空间、一账号多空间、严格对齐 WeKnora（含前端技术栈，界面照抄，后端用 Python 按 WeKnora 逻辑翻译）、第 1 阶段范围。下列"确认结果"优先于正文中与其冲突的表述。实施按 `tasks.md`，界面与接口对齐见 `design.md` 第 9 节。

## 背景

1. **空间只有一种形态**。当前 `tenants` 表没有类型，`create-owner` 创建公司空间，其余用户由空间管理员加入。个人用户没有自己的空间，也没有自助注册入口。
2. **账号没有手机号**。`users` 只有 `display_name`；密码账号的登录标识是 `user_identities`（provider `password`，scope 为空，external_id 为用户名），登录请求只有 `username` 与 `password`。
3. **组织树由平台管理员维护**（`2026-11-01-user-org-management`）。树是全局的，绑定到空间，人员不自动成为成员。企业自己无法维护自己的部门。
4. **企业微信只做扫码登录与绑定**（`auth/wecom.py`）。绑定关系是 `(wecom, corp_id, userid)`，未绑定的企业微信用户不会自动创建账号。当前没有通讯录同步：`WeComDirectory` 只有生成授权地址与换取 userid 两个方法，部门和成员都不从企业微信读取。

用户的需求：空间分两类，注册时选择企业或个人。个人保持现有逻辑。企业可以维护子公司、部门、成员（账号、手机号、密码），成员可以由企业管理员创建或邀请，也可以申请加入（需审批）。企业空间的设置里要有组织、部门、用户、角色和权限分配的维护界面。

## 确认结果（2026-11-03）

1. **一账号多空间**：每个账号有自己的个人空间，也可以加入企业空间。登录后选择进入哪个空间，之后可切换（对应 WeKnora `POST /auth/switch-tenant`）。
2. **严格对齐 WeKnora**：页面结构、路由、交互、文案（中英文）、API 路径与请求/响应结构、错误码都以 WeKnora 固定版本 `e1f9a6166` 为准。界面照抄，后端用 Python 按其逻辑翻译，不搬运 Go 代码。
3. **前端技术栈与 WeKnora 一致**：Vue 3、TypeScript、`tdesign-vue-next`、`pinia`、`vue-router`、`vue-i18n`、`axios`。`apps/web` 整体从 Element Plus 迁移到 TDesign，不做混用。这取代 `2026-11-02-weknora-parity` 决定 1。
4. **第 1 阶段范围**：空间、登录、组织、权限、设置相关页面与接口。侧栏和设置的菜单项全部补全，尚未实现的页面显示占位。其余功能（对话、知识库、智能体等）按父提案另提子提案。
5. **重写 Web 与 API，不在现有实现上调整**：`apps/web` 与空间、登录、组织、权限、设置相关的 `apps/api` 路由按 WeKnora 重写。现有的接口路径、响应结构和页面不作为约束，开发阶段不保留兼容层。
6. **登录标识改为邮箱加密码**：WeKnora 使用邮箱（`LoginRequest.email`）。本阶段取消手机号登录与手机号字段，决定 2、10 及相关表格中的 `phone` 作废。
7. **角色使用 WeKnora 的四级角色**：`owner`、`admin`、`contributor`、`viewer`（`tenant_members`，对应 `TenantRole`）。决定 4、7、8、11 中的 `member`、`admin`（作为成员角色）按此替换。
8. **组织有两层含义**：
   - WeKnora 的"组织"是跨空间的共享组（邀请码、加入申请、组织内角色 `admin`/`editor`/`viewer`）。它是"组织"页面的主体，按 WeKnora 实现。用户确认这就是共享空间。设置与侧栏中该入口的界面文案改为"企业"；路由、接口与代码名保持 `organizations`。
   - 企业内部的子公司与部门树（决定 3、7、9）是本仓库的扩展，放在企业设置的"组织架构"中，并在 `design.md` 的扩展清单中列出。
9. **沿用的已确认建议**：开发库直接重建（需确认第 3 条的方案 A）；平台管理员只有只读汇总（第 4 条）；部门不继承角色、按人分配并支持按部门批量选人（第 5 条）；企业微信只做登录与绑定，记录 `corp_id`（第 6 条）；注册时暴露邮箱是否已存在，与 WeKnora 一致（第 7 条）；申请理由选填，拒绝后冷却 7 天，成员可以退出，owner 除外（第 8 条）；一人一账号（第 9 条）。
10. **注册**：个人注册与企业注册都按 WeKnora `POST /auth/register` 的字段（用户名、邮箱、密码），并增加空间类型。不做短信验证码。企业注册开关由平台配置控制。

## 决定（建议，待确认）

1. **空间分类型，同一张表**：`tenants` 增加 `kind`，取值 `personal` 或 `enterprise`。注册时选择类型：选个人，创建个人空间；选企业，创建企业空间并把注册人设为 owner。
2. **个人空间沿用现有逻辑**：只有本人，个人模型、个人 Native 默认值、记忆与会话不变。个人空间本身不接受成员；个人用户可以申请加入企业（见决定 11）。
3. **企业空间是组织的所有者**：组织树（子公司、部门）属于企业空间，不再由平台管理员管理，也不再绑定到空间。这取代 `2026-11-01-user-org-management` 中"平台管理员维护树并绑定空间"的决定，见第 5 节。
4. **企业成员**：企业管理员可以创建账号（仅当手机号尚不存在时，设置初始密码，首次登录须改密），也可以邀请已有账号加入。成员也可以申请加入（见决定 11）。管理员可以重置密码、禁用成员、调整部门和角色。
5. **登录方式统一**：账号（手机号或用户名）加密码登录。登录后若用户属于多个空间，进入空间选择页（个人空间与所属企业），默认进入上次使用的空间；进入后可在用户菜单中切换空间。企业编码不参与登录，只用于查找企业以申请加入。
6. **一人一账号，多个空间身份**：`users` 全局唯一（手机号全局唯一）。个人空间与每个加入的企业都是这个账号的一种成员身份。这取代此前"企业账号与个人账号互相独立"的决定：不再为企业单独创建账号，因此不存在用创建企业账号接管个人账号的问题。管理员对已存在手机号的人只能发出邀请，不能设置其密码。
7. **部门与成员的关系**：每个企业账号在本企业内有且只有一个主部门，可以另加多个部门。用 `user_org_units` 表保存（增加 `tenant_id`），主部门约束从"每人全局一个"改为"每人每个企业一个"。`tenant_memberships` 保持不变，成员记录表示"在空间内有身份"，部门只表示组织位置，不决定权限。
8. **角色按人分配，部门不继承角色**：沿用 `tenant_user_roles`，不新增部门级角色表。界面提供"按部门批量选人分配角色"的操作，每次分配写入审计。部门级继承会让权限难以追溯，留到以后再定。
9. **企业微信保持现状**：本阶段仍只做扫码登录与绑定。企业空间可以绑定企业微信 `corp_id`（作为 scope），但通讯录同步（读取部门与成员）需要单独的通讯录密钥，留到后续提案。数据模型上给 `org_units` 留出 `source` 字段（`manual` 或 `wecom`）。
10. **手机号**：`users` 增加 `phone`（可空），全局唯一（部分唯一索引，忽略空值）。注册时若手机号已存在，会提示该手机号已有账号，这意味着注册页会暴露手机号是否已注册，见需要确认的项第 7 条。
11. **申请加入**：已登录用户通过企业编码找到企业，提交申请（理由选填）。同一人对同一企业同时只能有一条待处理申请，申请人可以撤回。企业管理员在"成员"页的待审批队列中处理：通过时指定部门（必选）与角色（默认 member，可选 admin，不能指定 owner）；拒绝时填写原因，并在冷却期内限制再次申请（建议 7 天）。
12. **邀请**：企业管理员按手机号或账号邀请已有用户，选择部门与角色；用户在空间选择页接受或拒绝。接受后成为成员（`source = invitation`）。成员可以主动退出企业，owner 除外；退出后成员记录标记为 `revoked`，部门记录与审计保留。申请、审批、邀请、退出全部写入审计。

## 数据模型变化

| 表 | 变化 |
| --- | --- |
| `tenants` | 增加 `kind`（`personal` 或 `enterprise`，非空，默认 `enterprise` 仅用于迁移已有数据，见需要确认的项）与 `wecom_corp_id`（可空，只记录，见决定 9）。 |
| `users` | 增加 `phone`（可空，全局唯一）与 `must_change_password`（布尔，默认否）。 |
| `user_identities` | 所有密码账号统一为 provider `password`，scope 为空；不再为企业单独写入 scope。 |
| `org_units` | 增加 `tenant_id`（必填）与 `source`（`manual` 或 `wecom`）；每个企业一棵树，树根由企业创建。 |
| `user_org_units` | 增加 `tenant_id`；主部门唯一约束改为 `(tenant_id, user_id)`。 |
| `tenant_org_bindings` | 企业空间不再需要绑定。表保留给迁移使用，迁移完成后删除（由需要确认的第 3 项决定）。 |
| `tenant_memberships` | `source` 允许值改为 `manual`（管理员创建）、`invitation`（邀请接受）、`application`（申请通过）；取消 `organization`（它依赖的绑定关系已取消）。 |
| `space_join_requests`（新表） | 申请与邀请：`tenant_id`、`user_id`、`direction`（`application` 或 `invitation`）、`status`（`pending`、`approved`、`rejected`、`withdrawn`）、`message`、`reject_reason`、`unit_id`、`role`、`requested_by`、`reviewed_by` 与时间字段。同一人同一企业仅允许一条 `pending`。 |

## 范围

范围内：

- 注册：个人注册、企业注册（两个入口，同一页面选择类型）。
- 统一登录（手机号或账号 + 密码）与空间选择；首次登录强制改密。
- 申请加入与邀请（待审批队列、拒绝冷却、成员主动退出企业）。
- 企业设置：企业信息、组织架构（子公司与部门，增删改移动，停用）、成员（账号的增删改、禁用、重置密码、部门归属、角色）、角色与权限（自定义角色、菜单与 API 权限，沿用 `authz/catalog.py`）、按部门批量分配角色、审计。
- 个人设置：与现状一致。
- 空间切换：用户可以属于多个空间（个人空间与所属的企业空间），切换器只列出自己有身份的空间。
- 迁移：已有空间、组织树与绑定（方案见需要确认的第 3 项）。
- 企业微信：保持现有登录与绑定，企业空间可绑定 `corp_id`（只记录，不同步）。

范围外：

- 企业微信通讯录同步（部门与成员读取）。
- 部门级角色继承。
- 个人账号与企业账号的关联。
- 邀请码（链接）加入。本阶段只有申请与邀请两种方式。
- 短信验证码（注册与找回密码）。第一版不接入短信服务。
- 计费与配额。

## 需要你确认的项

每项给出建议。

1. **注册与登录**
   - 个人注册是否需要短信验证码？建议：第一版不做，手机号加密码注册，后续接入短信。
   - 企业注册是否公开？建议：公开，注册人成为企业 owner；平台提供开关，可以关闭公开注册，改由平台管理员开通。
   - 企业编码：建议由注册时填写，全平台唯一，用于查找企业以申请加入（不参与登录）。
2. **登录标识**：建议手机号或账号加密码，全局统一。企业编码只用于查找企业以申请加入，不参与登录。找回密码第一版由管理员或平台重置，不做短信找回。
3. **现有数据如何处理**：当前是否有需要保留的生产数据？
   - A. 开发库，直接重建（建议，最简单）；
   - B. 有数据：现有空间全部标为 `enterprise`；每棵已绑定的组织树，若只绑定一个空间则归该空间，若绑定多个空间则复制为多棵树。
4. **平台管理员的组织权限**：建议保留系统级只读查看（列出企业与组织数量，不能修改企业内部结构）；企业内部结构只由企业管理员维护。
5. **部门角色**：建议按人分配，并支持按部门批量选人分配（见决定 8）。是否需要部门继承角色？建议：本阶段不做。
6. **企业微信**：建议本阶段保持登录与绑定，企业空间只记录 `corp_id`；通讯录同步另提案。是否同意？
7. **注册时暴露手机号是否已注册**：决定 10 会让注册页提示"手机号已有账号"。建议：接受，这是常见做法，而且已登录用户可以直接创建企业，不需要新账号。如果要隐藏，注册页只能统一提示，代价是企业注册时手机号已存在的情况要另行处理。
8. **申请规则**：申请理由是否必填？建议：选填。拒绝后冷却期多久？建议：7 天。成员能否主动退出企业？建议：能，owner 除外。
9. **一人一账号（决定 6）**：这取代了之前"企业账号与个人账号互相独立"的决定。请明确确认，它是本次变化里影响最大的一条。
10. **组件库（与已确认的 `2026-11-02-weknora-parity` 决定 1 冲突）**：该决定保留 Element Plus。"严格按照 WeKnora 前端"意味着 TDesign（WeKnora 前端使用 `tdesign-vue-next`）。建议：改用 TDesign，并在本提案中明确取代 parity 决定 1；否则只能在 Element Plus 上模拟，无法做到严格对齐。

## 验收

- 注册时可选择个人或企业；个人注册后直接拥有个人空间；企业注册后注册人为企业 owner。
- 个人用户看不到任何企业相关入口；企业成员看不到企业管理入口，除非角色允许。
- 企业管理员可以创建、禁用、重置账号，并维护组织树与部门归属；所有写操作写入审计。
- 登录失败（账号或密码错误）返回统一信息，不泄露账号是否存在。
- 新建账号首次登录必须改密，改密前不能访问其他页面。
- 管理员对已存在手机号的人只能发起邀请，不能设置其密码；只有手机号不存在时才能创建账号并设置初始密码。
- 用户可以申请加入企业；管理员通过后成为成员，拒绝后冷却期内不能再次申请；同一人对同一企业只能有一条待处理申请。
- 多空间用户登录后可选择空间，切换后看到的身份与权限随之切换。
- `uv run --locked pytest` 覆盖：空间类型、登录分支、部门主属约束、角色分配、迁移；浏览器测试覆盖注册与企业设置。
