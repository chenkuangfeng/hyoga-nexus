# 设计

## 数据模型

- `sessions.revision`：整数，默认 0，每次影响提示词可见内容的写入在同一事务内 `+1`。
- 已有的事件序号（`run_events.sequence` 或会话内消息序号）作为增量读取的水位。

## 缓存条目

键：`session_id`。值：

| 字段 | 内容 |
|---|---|
| `revision` | 装配时的会话修订号 |
| `watermark` | 已投影到的最大事件序号 |
| `history_view` | 按事件投影后的消息视图（含压缩摘录） |
| `checkpoint` | 工作检查点 |
| `bindings` | 智能体版本、模型配置版本、记忆快照引用 |

缓存条目不包含任何授权判断、凭据明文或工具执行结果的原始输出（超阈值的输出只保留引用句柄，与 2.5 节一致）。

## Run 开始时的装配

1. 读取 `sessions.revision`（主键查询）。
2. 缓存缺失：全量读取，写入缓存。
3. 缓存的 `revision` 等于当前值：直接使用。
4. 当前值更大：读取 `sequence > watermark` 的事件，增量投影，更新 `watermark` 与 `revision`；若绑定或检查点变化，一并刷新。
5. 增量读取失败或投影校验不通过：丢弃条目，全量重建。

## 失效与一致性

- 修订号是唯一的失效依据。同进程写入直接刷新缓存；跨进程写入靠 Run 开始时的检查发现。
- 缓存永远不会比数据库"更新"：只可能落后，落后时在 Run 开始时补齐。
- 在 Run 进行中，缓存不会被其他进程修改的数据所替换；该 Run 基于开始时的快照执行，下一个 Run 再补齐。这与现有的"Run 内前缀冻结"一致。

## 容量与回收

- 进程级上限：最多 `max_sessions` 个条目，超出按 LRU 淘汰。
- 单条目字节上限：超过则只缓存检查点和最近 N 条消息，较早内容每次从数据库读取（仍走增量读取）。
- 空闲 TTL：超过 `idle_ttl` 未使用的条目被回收。
- 默认值待定，实施时用测量结果确定。

## 与 Hermes 的差异

Hermes 缓存的是整个 Agent 对象，对象内部持有状态。本方案只缓存**数据**，执行对象每次 Run 重建。这样缓存可以随时丢弃，不影响正确性，也不要求会话粘在某个 worker 上。

## 测试要点

- 命中、缺失、增量、不一致后全量重建四条路径各有测试。
- 两个进程共享数据库：进程 A 写入后，进程 B 的下一个 Run 能读到新内容（修订号检查）。
- 权限撤销后，同一会话的下一次工具调用被拒绝（证明权限没有被缓存）。
- 缓存超过上限时按 LRU 淘汰，淘汰后结果与数据库一致。
- 进程重启后缓存为空，行为与缓存命中时一致。

## 未决问题

1. 默认 `max_sessions`、单条目字节上限、`idle_ttl` 取值。
2. 是否在第二阶段加入通知机制（如 PostgreSQL `LISTEN/NOTIFY`）以主动失效。当前方案不需要它。
3. 模型客户端与工具注册表是否也按配置版本缓存。它们与会话无关，可以作为单独任务。
