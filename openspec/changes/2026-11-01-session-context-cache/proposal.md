# 执行模型：每 Run 新建执行对象，会话状态为数据快照

## 状态

已确认（用户确认四项决定）。架构文档 1.2、2.2、2.12 与路线图第 2、3 步已同步修改。代码实施按 tasks.md 分阶段进行。

确认的决定：
1. 单机版 API 与 worker 分离为两个进程（不采用单进程网关）。
2. 崩溃恢复：上一代际未完成的执行标记为 `unknown`，会话阻塞，显式解除，不自动重放。
3. 每个 Run 读取一次会话头（水位与快照版本），接受该成本。
4. 架构文档与路线图在确认后修改（已完成）。

## 原因

参考项目的结论（见 design.md 第一节）：

- Hermes 按会话缓存 Agent 对象，是单写者进程内的特例。
- deer-flow 与 dify-agent 每次 Run 新建执行对象，会话状态是数据快照，存在数据库中。WeKnora 每轮新建引擎，也没有会话对象缓存。

我们的单机版和多租户版采用同一模型：

- 执行对象每次 Run 新建，不缓存。
- 会话状态只保存为可序列化的数据（快照），不保存句柄、客户端或模型对象。
- 会话数据的缓存用不可变 key（`session_id` + 水位），不做失效，多个进程共享也不需要协调。

## 范围

范围内（单机版与多租户版共用）：

- **执行对象每次 Run 新建**：引擎、工具网关、运行上下文都在 Run 开始时构建，Run 结束即释放。
- **进程级共享的无状态对象**：模型客户端、工具注册表，按配置版本构建一次，供所有 Run 共用。
- **会话状态快照**：版本化的 JSON（`schema_version`，当前为 2），只包含数据。Run 结束时（成功、失败、取消都要）在 `finally` 中保存终态快照。未执行的工具调用标记为 `interrupted`，保证下一轮的历史合法。
- **投影缓存**：key 为 `(session_id, watermark)`，值为由快照和事件投影出的会话视图。新事件产生新水位，即产生新 key；旧 key 按 LRU 与空闲 TTL 淘汰。没有失效步骤。
- **写入乐观并发**：追加事件与保存快照时带上预期水位，水位不一致则拒绝并重新读取。这样即使两个进程竞争，也不会静默覆盖。
- **派发账本**（保留）：CAS 领取、按 epoch fencing、启动恢复时把未完成执行标记为 `unknown` 并阻塞会话。这一条与 deer-flow（标记 `error`）不同，我们保留，因为工具调用可能已产生副作用。
- **忙时策略、队列上限、全局活跃会话上限**（保留 Hermes 的规则）。

不在范围内：

- **权限判断不缓存**（已确定）：每次工具调用与资源访问查库。
- 会话所有权（lease）与所有权感知领取（原方案的 R2、R4 中的所有权部分）：不再需要，因为缓存 key 不可变，多进程不会读到不一致的数据。CAS 领取保留。
- Redis：不引入。投影缓存先用进程内实现，多进程共享需要时再换成共享存储，接口不变。
- 渠道层的回复路由（由渠道阶段处理）。

## 与之前结论的差异

1. **不再满足"每次 Run 不读库"**。每个 Run 仍需读一次会话头（当前水位与快照版本），这是一个主键查询。它不读会话内容，内容由投影缓存提供。单机版是本地 SQLite，这次读取的成本很低。
2. **不再保留"单进程"的必要性**。单机版的进程模型可以是单进程网关，也可以是多进程，缓存正确性都不依赖进程数。是否保留单进程网关，由你决定（见下文）。
3. **执行对象不缓存**。这与之前"单机版缓存会话对象"的方案不同。执行对象每次新建，代价是构建开销，因此模型客户端与工具注册表做成进程级共享。

## 需要确认的决定

1. 单机版进程模型：单进程网关（API 与 Run 同进程），还是 API 与 worker 分离（deer-flow 的方式，靠租约回收孤儿 Run）？推荐：单进程，因为单机版部署简单，崩溃后的恢复由账本负责。
2. 崩溃恢复：`unknown` 阻塞会话（推荐，保留 Hermes 的行为），还是 `error` 并允许重试（deer-flow）？
3. 会话头读取是否可以接受（推荐：接受，它是本地主键查询）。
4. 架构文档 1.2、2.2、2.12 与路线图第 2、3 步的修改，在确认后再做。

## 影响

- 架构文档 2.2（恢复规则）与 2.12（会话与持久化）需要改写：执行对象不缓存，状态为数据快照，投影缓存用不可变 key。
- 路线图第 2 步新增快照版本、乐观并发写入；第 3 步新增执行模型、投影缓存、终态快照规则。
- 数据库：新增快照表（或在会话表中增加快照列）与水位字段。这是持久化模型变化，需要确认。

## 并入：全局活跃会话上限（原 session-concurrency-limit 提案）

原独立提案已并入本变更，并按其推荐方案实施（用户要求继续实施）：

- 超限时提交新会话被拒绝，返回 503 `session_capacity_exceeded`，不写入任何记录。
- 默认上限 8，配置项 `configs/nexus.toml [platform].max_concurrent_sessions`；非法值失败关闭。
- 计数范围为全部租户合计；占用名额的会话 = 持有 `queued`、`started` 或 `unknown` 记录的会话。草案只计 started 与 unknown，但只在提交时检查时，排队会话被领取后会超出上限，因此排队会话也计入。
- 只有新会话的提交检查上限，同一会话的后续 Run 不占新名额。
- PostgreSQL 下计数与插入不在同一锁内，精确性随任务 2.9 补齐。
