## 执行顺序与交付门槛

1. Native 核心：执行循环、完成判断、模型协议、上下文/记忆、hooks、审批挂起与恢复。逐个模块记录输入输出、分支、异常、原测试、Nexus 实现位置与差异。
2. 平台能力：身份授权、配置版本、资源、事件与持久恢复。沿 Native 调用链核对相关服务、类型、API 和前端入口。
3. 外围能力：知识库、技能/MCP、协作调度、渠道、桌面与产物。完整保留归属和差异；暂缓不等于审查完成或免除迁移。
4. 汇总批次提案：列清保留行为、冲突方案、兼容证据和前端配置，按仓库规则确认后实施新增范围。

每批审查结果区分全文阅读、定点阅读、静态发现、已运行测试和未验证能力。模块证据见 [插件审查](reference-hooks-review.md)与[模型协议审查](reference-model-review.md)。

## 工作量与估算限制

此前“数天”的表述缺少规模统计，不能作为全量交付承诺。全量有近五千索引项，且已有标记不能证明全文完成；全量审查按连续工作的数周级以上预留更合理，复杂的跨包行为核对和差分测试可能进一步增加时间。此处为粗粒度容量判断，不是经过实测的工期。

Native 核心与全量外围分开跟踪，但不缩减用户要求。下一次更细估算应基于至少一个核心模块的实际审查耗时、分支数及测试可运行性；当前没有足够测量数据，暂不为各组编造精确日期。源码审查、方案确认、实现迁移和真实环境验收分别计时。

本清单按已有索引逐项归组，未重新证明上游整个 Git 树已被索引覆盖，也未逐项重新验证全部来源哈希。目录/符号链接/缺失项应先确认其实际类型与 Git 对象，再决定阅读方式；不能因本地无法按普通文件读取而标记完成。
