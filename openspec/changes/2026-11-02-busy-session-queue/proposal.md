# 忙时排队：同一会话的新消息进入 FIFO 等待

## 状态

待确认。确认前不修改提交接口，也不实现派发变更。

## 原因

当前会话已有活跃 Run 时，提交新消息返回 409（"Session already has an active Run"）。Web 工作台和企业微信用户都会在模型还在回答时继续发消息，409 迫使前端自行重试或提示用户等待，体验差。

Hermes 默认打断当前轮。我们不采用默认打断：工具调用可能已产生副作用，打断后结果未知会进入 `unknown` 并阻塞会话。因此默认改为排队，打断只作为用户显式停止（现有取消接口）。

## 范围

范围内：

- 忙时提交：会话已有非终态 Run 时，新 Run 以 `queued` 入队，提交返回 202，并携带 `queue_position`（从 1 起算，表示前面还有几条待执行）。
- 队列上限：每会话待处理（`queued`）条目不超过 32。超限返回 409，错误码 `session_queue_full`。
- 派发顺序：worker 只执行会话 FIFO 的队首。领取时若不是队首，释放租约并稍后重试，不标记失败，不执行。
- 取消排队中的 Run：状态变为 `cancelled`，FIFO 条目由终态钩子释放（已实现）。
- 事件：`run.queued` 事件的 payload 增加 `queue_position`。

范围外（明确不做）：

- 默认打断。打断只通过现有取消接口显式触发。
- 转向（steer）。以后单独提案。
- 排队超时。排队中的 Run 不会自动过期，用户可以取消。
- 全局 `max_concurrent_sessions` 上限。另行提案。
- 企业微信渠道的回复路由。由渠道阶段处理。

## 接口变化

| 场景 | 当前 | 变更后 |
|---|---|---|
| 会话空闲，提交 | 201，`status=queued` | 不变 |
| 会话忙，提交 | 409 | 202，`status=queued`，`queue_position` |
| 会话忙且队列已满 | 409 | 409，`session_queue_full` |
| 幂等重放 | 原结果 | 不变 |

## 派发变化

- `claim_session_admission` 目前对非队首直接报错。变更为：返回"暂不可领取"，worker 释放 Outbox 租约并设置 `available_at = now + 退避`（初值 2 秒），Run 保持 `queued`。
- 队首被领取后按现有流程执行，终态时释放 FIFO。
- 不因等待而写失败事件，避免事件流噪声。

## 需要确认的决定

1. 忙时提交返回 202（推荐），还是 201（与空闲时一致，靠 `queue_position` 区分）？
2. 派发退避初值 2 秒是否可接受？
3. 排队中的 Run 是否允许用户修改或撤回（推荐：只允许取消，不允许修改）。

## 影响

- API 契约：`docs/architecture.md` 2.12 的提交语义与路线图第 3 步需要同步修改。
- 数据库：无新表。`run.queued` 的 payload 变化不需要迁移。
