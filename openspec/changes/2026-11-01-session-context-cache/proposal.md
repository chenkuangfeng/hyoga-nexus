# 单机版改为 Hermes 式网关进程

## 状态

待确认。确认前不编码，也不修改架构文档与路线图。

## 原因

单机版目前是 API 进程 + 独立 worker 进程，Run 通过数据库 Outbox 派发给 worker。这种结构下：

- 会话数据可能被 API 和多个 worker 写入，任何进程的缓存都可能过期，所以会话缓存需要所有权或修订号校验。
- 每个 Run 重建执行对象，执行结束即丢弃，没有会话级复用。

Hermes 的做法是单进程网关：同一进程内接收消息、持有每个会话的 Agent 对象（缓存），会话的写入都由该进程完成。这样进程内缓存不存在多写者问题，会话数据可以只在进程内读取，不用每个 Run 读库。

本提案把单机版改为这种模式，并保留 Hermes 的持久化账本（CAS 领取、epoch fencing、`unknown` 恢复）用于崩溃恢复。

## 范围

范围内（仅单机版）：

- 单进程网关：API 与 Run 执行在同一进程内，不再有独立 worker 进程。部署形态为一个进程。
- 每个会话在进程内持有一个会话对象，包含会话数据与执行对象（Hermes 的 `_agent_cache` 思路）。Run 结束后保留该对象，供同一会话的下一个 Run 复用，空闲超时后释放。
- 会话内串行与忙时策略、队列上限、全局活跃会话上限，按 Hermes（见 design.md）。
- 持久化账本（SQLite）：admission（queued → started → terminal / unknown）、进程 epoch、执行记录。领取用 CAS。
- 启动恢复：上一代 epoch 的 started 与执行记录标记为 `unknown`，会话阻塞，需要显式解除，不自动重放。
- 进程退出时：停止接收新 Run，等待正在执行的 Run 结束或超时，未完成的标记为 `unknown`。

不在范围内：

- **权限判断不缓存。** 每次工具调用和资源访问查数据库（这一条已确定）。
- 多租户部署。多租户保留 API + worker + PG + Redis 的结构，另行提案，不受本提案影响。
- 派发到多进程。单机版不支持多个网关进程同时服务同一数据库；需要多进程时属于多租户部署。
- 渠道层（企业微信等）的回复路由，由渠道阶段处理。

## 变更内容

- 删除单机版对独立 worker 进程的依赖。`apps/worker` 的单机入口不再作为必需部署项；多租户入口保留。
- 新增进程级 `runtime_epoch`：每次进程启动递增，所有账本写入带当前 epoch，过期 epoch 的写入失败（`stale_epoch`）。
- 会话对象缓存：有界（`max_sessions`、LRU、空闲 TTL）。缓存的数据包括历史投影、检查点、绑定、记忆快照引用、执行对象。缓存不包含授权结果。
- 同一会话的 Run 串行；忙时默认打断，queue、steer 为可选。
- 持久化队列每会话上限 32；全局 `max_concurrent_sessions` 超限拒绝新会话。

## 影响与待确认

1. **是否接受单进程部署**：API 与 Run 同进程，API 重启会中断正在执行的 Run，这些 Run 进入 `unknown`，需要人工解除。这是 Hermes 的代价。
2. **执行对象是否缓存**：Hermes 缓存整个 Agent 对象。本提案建议缓存，但执行对象必须可重建，恢复逻辑不依赖它（架构 2.2）。
3. **多租户是否保持 worker**：本提案假设是。如果多租户也要改，需要另行提案。
4. **是否修改架构文档**：1.2（总体结构）、2.2（恢复规则）、2.12（队列、数据库）需要同步改写，路线图第 2、3 步也需要改。这些改动在确认后再做。
5. **数据库**：单机版使用 SQLite 账本，PG 不再是单机版必需项。这与架构 2.12 的"PG 为事实源"冲突，需要明确：单机版事实源是 SQLite。
