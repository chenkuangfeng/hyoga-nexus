# 会话所有权、会话缓存与派发账本

## 状态

待确认。确认前不编码。

## 原因

当前 worker 每个 Run 都从数据库装配会话上下文，执行结束后丢弃全部对象。同一会话连续发消息时重复读取历史，且不存在任何会话级缓存。另外，派发（领取 Run）、恢复（进程崩溃后的 Run）和并发（同一会话多个 Run）的规则还没有写成可验证的契约。

参考 Hermes 的做法，本提案把三件事一起定下来：

1. **会话所有权（lease + epoch）**：同一会话同一时刻只由一个 worker 进程持有，持有者在进程内缓存该会话的全部数据，Run 期间不再读库取会话数据。
2. **派发账本**：领取 Run 使用条件更新（CAS）加 rowcount 检查；每次写入带所有权 epoch 做 fencing；上一代进程遗留的未完成执行标记为 `unknown`，不自动重放，并阻塞该会话直到人工或显式恢复。
3. **会话缓存**：缓存会话历史投影、检查点、绑定、记忆快照引用，以及同会话复用的无状态执行配置（模型客户端、工具注册表）。

## 范围

范围内：

- 会话所有权的获取、心跳、释放与过期接管（PostgreSQL 表，单机与多租户共用语义）。
- Run 领取改为所有权感知：worker 只领取自己持有所有权的会话、或未被占用的会话的 Run。
- 每次写库带 `owner_epoch`，过期 epoch 的写入失败（`stale_epoch`）。
- 启动恢复：epoch 小于当前值的 execution / admission 标记 `unknown`，会话进入阻塞态，需显式恢复。
- 进程内会话数据缓存（有界，LRU、空闲 TTL、字节上限），写入采用"先写库、提交后更新缓存"。
- 会话内 Run 串行；同会话新输入的处理策略（打断、排队、转向）作为可配置项，默认打断，与 Hermes 一致。
- 队列上限：每会话待处理 32 条，全局活跃会话数由 `max_concurrent_sessions` 限制，超限拒绝而非排队。

不在范围内（明确排除）：

- **权限判断不缓存。** 每次工具调用与资源访问仍查数据库。见"需要确认的推荐点"第 1 条。
- 派发的存储切换（单机 SQLite 适配器）与 Redis。本提案只定义端口，SQLite 实现另行提案。
- 通道层的回复路由与广播问题（WeCom 等前端），由渠道阶段处理，本提案只约定"回复按请求 ID 路由，不使用全局回调"。

## 变更内容

- 新表 `session_owners`：`session_id`、`owner_id`（worker 实例 ID）、`epoch`（单调递增）、`heartbeat_at`、`expires_at`。获取所有权用 `UPDATE ... WHERE expires_at < now() OR owner_id = :me`，并检查 rowcount；epoch 在接管时 `+1`。
- 新表或列 `session_admissions`（或 `runs.status` 扩展）：`queued | started | unknown | terminal`，领取用 `UPDATE ... SET status='started', owner_epoch=:e WHERE id=:id AND status='queued'`，rowcount 为 0 即放弃。
- 缓存内容：历史投影、检查点、绑定（智能体版本、模型配置版本、记忆快照引用）、无状态执行配置。缓存不含授权结果、凭据明文、超阈值工具输出原文（只存句柄）。
- 数据库仍然必须访问的场景：所有权获取与心跳、派发 CAS、写 Run 事件与账本、权限检查、会话首次装配（冷启动或接管时一次性全量读取）。
- 进程重启或失去所有权后，缓存整体丢弃；接管方从数据库全量重建。

## 影响

- 架构文档 2.2（恢复规则）与 2.12（队列、数据库）需补充所有权、epoch fencing 与 `unknown` 规则。
- 路线图第 2 步（平台底座）新增派发账本与所有权子任务；第 3 步新增会话缓存与装配子任务。
- 数据库迁移：新增 `session_owners`，修改 `session_admissions` / 执行状态字段。这是持久化模型与派发行为的变化，需要确认。
- 运行时行为变化：领取规则从"任意 worker 领取任意 Run"变为"所有权感知领取"。需要确认。
