# Run 累计 Token 预算改为可选

## 背景

Native Run 当前把累计模型 Token 用量硬性限制在 `max_tokens` 内，超过后以 `budget_exhausted` 终止。WeKnora 与 Hermes 主要以模型上下文窗口触发历史压缩，并由轮数、时长等执行上限约束一次执行；累计 Token 更适合作为可选成本护栏，而不是默认终止条件。

## 变更

- `max_tokens=0` 表示不限制一次 Run 的累计 Token 用量；默认值改为 0。
- 大于 0 的 `max_tokens` 继续作为可选硬上限，保持既有部署可显式设置成本护栏。
- 每次模型请求仍受 `max_output_tokens`、上下文窗口 token 预算、轮数、时长、错误数和请求次数约束；上下文压缩继续独立运行。
- 模型档案与智能体分别配置上下文窗口，数值以 K tokens 维护（如 128K、256K）；智能体可跟随模型或设置更小上限。
- Native 压缩与请求拟合统一使用生效上下文窗口的 token 估算。
- 子智能体在父 Run 无累计 Token 上限时不再因累计用量拒绝启动；父 Run 配置了上限时继续按剩余额度分配。
- 文档梳理 WeKnora、Hermes 与本仓库的触发、压缩后上下文传递和压缩无法达标时的行为。
- 将 Nexus 现有追加式摘要链作为会话级正式上下文起点，串行保护检查点推进，并在供应商上下文溢出时强制压缩、裁剪旧工具结果后重试一次。

## 非目标

- 不取消模型供应商自身的上下文或输出上限。
- 不删除或改写原始会话消息、Run 事件和工具执行记录。
- 不移除最大回合、最大活跃时长、最大错误数和最大模型请求次数限制。

## 验收

- 默认 Run 可累计超过 16,000 Tokens 后继续，直到其他 Run 限制或任务完成。
- `max_tokens>0` 时仍在累计预算耗尽后停止。
- 不受累计预算约束的模型请求仍执行上下文整理，并采用独立的单次输出上限。
- 三个项目的压缩后消息传递及二次超限处理有源码依据和文档说明。
- 后续 Run 使用最新授权有效摘要和边界之后的消息；压缩并发不能倒退检查点；供应商上下文溢出最多进行一次压缩恢复重试。
