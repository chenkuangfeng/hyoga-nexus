# 用户组织管理：组织树与空间绑定

## 状态

已确认（2026-11-01）：第 2 项选方案 A，第 3 项选方案 C，其余决定见下。已实施，完成情况见 tasks.md。

## 范围

范围内：

- **组织树**：一棵树可以表示集团、子公司和部门。根节点是组织（集团），子公司是集团下的节点，部门是子公司下的节点。层级不限。支持新建、重命名、移动、停用节点。
- **人员归属**：人员就是现有的 `users`。用户可以挂到一个或多个节点，其中必须有且只有一个主节点。
- **空间与组织的绑定**：一个空间可以绑定多个组织节点（例如集团空间绑定集团根节点，或绑定若干子公司节点）。绑定由组织管理员单方面完成。
- **空间内的展示**：空间成员可以看到所绑定的组织、组织的部门树，以及组织内的人员列表。这些人员与空间成员（`tenant_memberships`）分开显示。
- **组织管理页面**：组织管理员维护组织树、人员归属、查看已绑定的空间。
- **审计**：组织结构变更、人员归属变更、绑定与解绑都写入审计记录。

范围外：

- 创建或停用全局用户账号（沿用现有的登录与账号创建流程）。
- 从企业微信、IdP 或 SCIM 同步组织结构。
- 组织人员自动加入空间。人员加入空间的方式见第 6 节第 2 项。

## 需求

1. 组织管理员可以创建组织（集团），在组织下创建子公司或部门，层级不限。
2. 节点不能移动到自己的子孙节点下，否则形成环，操作被拒绝。
3. 停用的节点不能作为新的人员归属或绑定目标，已有归属和绑定保留显示。
4. 删除节点前，节点下不能有子节点、人员归属或空间绑定。
5. 用户可以属于多个节点，但只能有一个主节点。设置新的主节点时，旧的主节点自动取消。
6. 组织管理员可以把空间绑定到任意有效节点；同一空间可以绑定多个节点。组织管理员和空间 owner 都可以解绑（默认设计，见"需要你注意的一点"）。
7. 空间成员可以看到：所绑定的节点及其所在组织的名称、部门树（绑定节点及其子树）、子树内的人员列表（去重）。
8. 空间的组织信息只对空间成员可见，非成员访问返回 NotFound。
9. 组织绑定不改变空间成员关系，也不改变用户的登录和权限判断。

## 与现有模型的关系

- 新增 `org_units`、`user_org_units`、`tenant_org_bindings` 三张表，不修改 `tenant_memberships`、`tenant_roles` 与 `users`。
- 组织人员不写入 `tenant_memberships`，因此不影响空间的权限判断。
- 绑定是 `tenant_id` 与 `unit_id` 的多对多关系。

## 影响

- 数据库：新增 `org_units`、`user_org_units`、`tenant_org_bindings`、`org_audit_records` 四张表，`users` 增加 `is_platform_admin` 列，共一次迁移（`d1f5b8c2a9e4`）。不新增组织管理员表。
- 权限：组织管理由平台管理员标识控制，不新增 API 权限或菜单键，权限目录（`authz/catalog.py`）不变。
- API：组织、节点、归属、绑定接口，以及空间的组织信息接口。
- Web：新增"组织管理"页面和空间设置页中的组织区域。UI 设计按 AGENTS.md 使用 `ui-ux-pro-max` 技能。
- 文档：更新 `docs/architecture.md`、`docs/roadmap.md`，并在模块文档中记录组织模型。

## 已确认的决定

1. **绑定方式**：组织管理员单方面绑定，不需要空间 owner 确认。
2. **可见性**：空间成员可以看到所绑定组织的部门树和人员。
3. **层级**：不限制层级，保留环检测。
4. **多组织**：一个空间可以绑定多个组织节点（集团空间）；子公司是集团树中的节点，绑定目标可以是任意节点。
5. **人员**：人员就是用户，归属通过 `user_org_units` 关联现有 `users`，不另建人员实体。

## 第 2、3 项的结论

- **第 2 项：人员加入空间采用方案 A。** 空间管理员从绑定子树的人员中勾选用户，批量加入为成员，角色可选（默认 `member`，不能指定 owner）。每次加入写入审计。接口为 `POST /api/v1/tenants/{id}/members/from-organization`。方案 B（用户自助申请）不在本次范围内。
- **第 3 项：组织管理员采用方案 C。** 在 `users` 上增加 `is_platform_admin` 布尔字段，由运维通过 `nexus_api.cli set-platform-admin` 设置。平台管理员可以管理全部组织树、节点人员、空间绑定，以及查询用户目录。

## 需要你注意的一点

- 方案 C 下，任何平台管理员都能管理所有组织树，没有按子树限定范围。如果以后需要集团与子公司分别管理，需要在 `users` 之外增加范围绑定。
- 绑定由平台管理员单方面完成，空间 owner 无法阻止。默认设计：空间成员能看到绑定的来源，空间 owner 可以解绑。如果不希望 owner 有解绑权，请告诉我。

## 范围收敛：先支持单集团

当前版本只支持一个集团（一棵组织树）。这次确定的范围如下。

**本阶段要做**

1. **分层授权（方案 C+）**：新增 `org_admins(unit_id, user_id, role)`，授权覆盖节点及其子树。集团管理员挂在根节点，分公司管理员挂在分公司节点，部门管理员同理。平台管理员仍保留 `users.is_platform_admin`，只负责组织生命周期（创建组织、授予组织管理员）。
2. **边界规则**：分公司节点本身由上级管理；移动节点时，源位置和目标位置都必须在操作者的管理范围内；分公司管理员可以绑定自己子树内的节点（绑定后通知上级）。
3. **员工去重**：`users` 增加可选的 `employee_no`，全平台唯一（单集团下即集团内唯一）。创建账号前按工号查找，已存在则只新增节点归属。
4. **根节点名称**：单集团下只有一个根节点，保留现有的唯一性检查，不做改动。

**本阶段不做**

- 集团编码（`code`）与按集团的命名空间。
- 按集团区分的主节点（本阶段每人仍只有一个主节点）。
- 跨集团的空间绑定确认、子公司跨集团迁移、合资（一个节点两个父节点）。
- `users` 上的集团字段（集团归属从节点的根节点推出）。

**多集团的扩展点（以后实现时使用）**

- 登录命名空间：`user_identities.scope` 作为集团编码，已有字段，不需要改表。
- 工号唯一范围：从全平台唯一改为 `(集团, employee_no)` 唯一，届时需要一次迁移。
- 主节点：`user_org_units` 的部分唯一索引改为 `(user_id, 根节点) WHERE is_primary`，需要冗余 `root_id` 列。
- 根节点名称唯一性：改为由集团编码保证。
- 空间绑定：跨集团节点的绑定增加双方确认状态。
