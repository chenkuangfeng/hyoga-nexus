# 运行监督 Watchdog：检测长任务停滞与偏离

## 状态

已确认（按推荐方案）。后端与 API 已实施；工作台提示与操作待办。实施状态见 tasks.md。

## 原因

Native Run 可以运行很久，目前只有两种结束方式：正常完成、用户手动取消。模型陷入重复工具调用、长时间没有进展，或者超出预期步数时，平台没有任何主动提示，用户只能等待或自行发现。

DeepSeek Super-agent 设计文章（见路线图 3.23 的参考说明）提出了外部 Watchdog：独立于 Agent 本体的监督回路，判断 Worker 是否有实质进展，必要时介入。它的价值在于监督者与执行者分离，不由同一个模型自己判断自己是否卡住。

本提案只做第一步：**检测并提示**，不做自动修复。

## 范围

范围内：

- 监督对象：处于 `running` 状态的 Run。
- 进展信号（规则，不依赖模型）：
  - 无进展超时：超过 `watchdog.idle_seconds`（默认 300 秒）没有新的 `run_events`，且没有等待用户输入或等待审批。
  - 重复调用：同一 Run 内，相同工具名与相同参数连续出现 `watchdog.repeat_threshold` 次（默认 3）。
  - 步数接近上限：逻辑回合数达到预算的 `watchdog.turn_warn_ratio`（默认 0.8）。本次不实现，见决定 5。
- 动作（仅限）：
  - 追加一条 `run.watchdog_alert` 事件，payload 含触发规则、阈值和观测值。
  - 将 Run 标记为 `attention_required`（新的展示标签，不改变执行状态机）。
  - Web 工作台展示提示，用户可以选择"继续等待"、"取消"或"发送提示"。
- 监督运行位置：worker 进程内的定时扫描协程，扫描间隔 `watchdog.interval_seconds`（默认 30 秒）。不新建进程，不新建 Run。

范围外（明确不做）：

- 模型判断"是否偏离目标"。作为后续提案，需要单独评估成本与误判率。
- 自动取消、自动重试、自动改写提示词。Watchdog 不直接修改执行结果，也不替代取消接口。
- 跨 Run 或跨会话的全局监督。
- 与渠道通知的集成（企业微信提醒等），留到第 9 步。

## 接口变化

- 新事件类型 `run.watchdog_alert`（只增不改，旧客户端忽略未知事件类型）。
- Run 响应增加 `attention_required: bool`，默认 `false`。
- 配置项 `[watchdog]`（写入 `configs/nexus.toml` 的新段，并同步更新 `configs/nexus.example.toml`）。

## 已确认的决定

1. **检测方式**：只用规则，不引入模型判断。模型判断另行提案。
2. **动作上限**：只提示与标记，不自动暂停或取消。
3. **运行位置**：worker 内协程，在执行监控循环中按间隔调用。
4. **默认阈值**：空闲 300 秒、重复 3 次、间隔 30 秒，作为估计值，待真实负载校准。
5. **回合数规则**：依赖路线图 3.15 的计数，本次不实现。本次只实现空闲与重复两条规则。
6. **属性派生（实施中调整）**：`attention_required` 由事件派生，不新增持久化字段，因此不需要迁移。
