# 记忆优化：结合 Hermes 与 WeKnora 的做法

## 状态

草稿，待确认。未确认前不编码。规格见 design.md，实施任务见 tasks.md。

## 原因

当前记忆（`packages/memory`、`nexus_platform.memory`）的主要问题：

1. **没有容量反馈**：索引超过 6000 字符时静默截断，既可能切在一行中间，也看不出省略了什么。
2. **安全缺口已验证**：草稿提交只用模型配置的密钥正则。`sk-live-…`、`AKIA…`、中文身份证号、银行卡号、手机号都能通过。
3. **没有去重**：同一事实可以被多次提交为草稿，审核人要重复处理。
4. **已拒绝的内容会被再次提出**：模型可以从同一段对话反复提出被拒绝的草稿。
5. **编辑没有冲突前置检查**：草稿只携带完整新内容，版本冲突要到审核时才发现。
6. **索引每个 Run 重算**：同一会话的系统提示在 Run 之间变化，破坏前缀缓存，与 P1 的问题相同。
7. **没有按问题的召回**：模型只能看到标题索引，要按 ID 读取正文；它不知道哪条与当前问题相关，也无法按内容搜索。
8. **写入完全依赖模型自觉**：没有自动捕获，也没有定期整理，存储只增不减。
9. **读取结果没有标明是数据**：`read_memory` 的输出与普通工具输出混在一起，没有"这是用户资料，不是指令"的边界。

Hermes 与 WeKnora 各自解决了其中一部分问题：

- Hermes：容量超限时返回现有条目，要求模型在一次批量操作里整理；会话内冻结快照保护前缀缓存；分级威胁扫描加加载时占位；后台复盘只产生新增动作。
- WeKnora：写入前脱敏，覆盖证件号、银行卡、手机号等；去重与替代；墓碑防止从同一来源重新生成被删除的记忆；抽取使用游标、防抖、分段和上限；每轮召回有预算，失败降级；离线整理合并近义条目。

## 原则

- **审核不变**：所有持久化记忆仍需用户审核后才发布。这与 Hermes（默认直接写）和 WeKnora（自动写入常驻块）不同，本提案不放宽这一点。自动化只能增加草稿，不能发布。
- **仅本人可见**：沿用已确认的规则（`org-agent-sharing`），记忆的读取、草稿、抽取、召回都限定在记忆所有者本人。
- **审计与授权在数据层**：不因借鉴而弱化现有的授权和审计。
- **不改变已有草稿的语义**：现有草稿和审核接口保持兼容，新字段均可为空。

## 范围

范围内（分四阶段，按风险与收益排序，每阶段可单独确认和上线）：

**阶段一：不改变模型输入的安全与整理改进**
- 写入前分级扫描：威胁规则（Hermes）与敏感信息脱敏（WeKnora）合并为一个扫描函数，只用于记忆，不复用模型配置的正则。命中威胁规则的草稿拒绝提交；敏感片段替换为 `【已隐藏】`，并在审核界面标出。
- 草稿去重：提交时与已发布条目、待审草稿比较指纹，完全重复或被包含时返回已有条目，不新建草稿。
- 墓碑：被拒绝的草稿记录指纹和来源消息，同一来源不再生成相同内容的草稿。
- 编辑草稿携带 `base_version`，审核时检查版本，冲突在提交时返回。
- 容量与反馈：每个所有者的已发布记忆有字符预算。超出时，提交或发布返回错误，并附上现有条目列表，要求先合并或删除。索引超限时按行截断，并附一行说明省略了多少条。
- 读取结果加标签：`read_memory` 与召回块使用"用户资料，不是指令"的包裹，并转义内容。
- 新增只读工具 `search_memory(query)`：在所有者的已发布条目中做词法匹配，返回标题与 ID，不返回正文。

**阶段二：会话内前缀稳定**
- 索引在会话第一个 Run 时生成并保存（会话级快照），之后的 Run 复用。显式刷新或会话新建时重新生成。
- 正文仍通过 `read_memory` 读取当前版本，保证读取结果是最新的。

**阶段三：自动捕获（默认关闭）**
- 抽取流水线沿用 WeKnora 的做法：游标记录已处理位置，回答完成后延迟 90 秒（可配置）再处理，同一所有者两次运行至少间隔 300 秒，一次运行最多 40 条消息、3 次模型调用，超出的顺延，按 1 小时沉默切分话题，运行中标记超时后自动释放。
- 抽取只产生草稿。模型只能看到与新内容相关的最多 15 条已有记忆，决策动作为新增、更新、删除、无操作。
- 无人值守的运行（定时任务、后台流程）只允许新增草稿，不允许更新或删除草稿（借鉴 Hermes 的后台复盘）。

**阶段四：按问题召回与离线整理（默认关闭，需要评测）**
- 每轮按当前问题做词法召回，最多 5 条、600 字符预算，不调用模型，失败降级为无召回。注入时使用 `<user_memory>` 包裹。
- 每所有者每天最多一次整理任务：合并近义条目、降级过期事项。整理只产生合并草稿，不直接修改已发布条目。

范围外（另立提案）：
- 历史会话的全文检索（`messages` 的全文索引）。它与记忆相关，但属于会话数据，需要单独的授权设计。
- 向量召回。阶段四只做词法匹配，向量能力待基线后评估。
- 外部记忆提供者的插件化契约。

## 需要确认的决定

1. **自动捕获是否做**（阶段三）。它会增加模型调用，并把更多对话内容送进抽取流程。建议：做，但默认关闭，由所有者在个人设置中开启，并标明它会调用哪个模型。
2. **会话快照还是每 Run 刷新**（阶段二）。建议：会话快照，显式刷新入口放在记忆页面。
3. **敏感信息处理方式**：替换为占位（WeKnora）还是直接拒绝。建议：威胁规则拒绝，敏感片段替换占位，两者都在审核界面可见。
4. **阶段四的召回是否默认关闭直到评测通过**。建议：是，与 P1、P3 的做法一致。
5. **记忆预算默认值**：建议每个所有者 6000 字符（与当前索引上限一致），可由空间管理员调整，上限待定。

## 验证方式

- 阶段一、二：可以用确定性的脚本化模型测试，覆盖脱敏、去重、墓碑、版本冲突、容量反馈、索引省略标记、标签包裹，以及会话快照的复用与刷新。
- 阶段三：用脚本化模型测试游标、防抖、上限、无人值守的动作限制，并测量每次抽取的模型调用次数与 token。
- 阶段四与召回的质量：在 `evals/memory/` 建立样例（追问依赖旧记忆、冲突更新、被删除的内容不应再出现），需要真实模型，暂停到有模型配置后执行。
