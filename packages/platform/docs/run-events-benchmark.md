# Run 事件通道压测与故障注入

对应提案 `2026-11-07-run-event-streaming` 的 8.1、8.2。设计见 [design.md](design.md) 的“Run 事件通道”。

## 压测

脚本：`evals/run-events/bench.py`（`uv run python evals/run-events/bench.py --backends memory,database,redis --redis-url redis://127.0.0.1:6391/0`）。测的是查看者感受到的延迟：生产者给事件打时间戳，订阅者收到时相减（同一进程同一时钟）。

- `database` 后端由提交的 `run_events` 行驱动（SQLite 文件）；它的 `publish` 本身什么都不做，所以没有发布耗时。
- 订阅者先于第一个事件连上；每个场景每 Run 200 个事件，100 个/秒（`runs_50` 为 100 个、50 个/秒；database 因 SQLite 单写者只给十分之一速率，否则测到的是生产者）。
- 环境：2 核、1.8 GB 内存的开发机，Python 3.11，Redis 6.2.24 本机回环，单个 worker 进程内生产。数字用来比较后端，不是容量上限。

### 查看者延迟（毫秒，p50 / p99）

| 场景 | memory | redis | database |
| --- | --- | --- | --- |
| 1 个订阅者 | 0.16 / 0.33 | 0.80 / 1.58 | 136 / 257 |
| 10 个订阅者 | 0.43 / 0.84 | 0.88 / 1.96 | 150 / 434 |
| 100 个订阅者 | 2.2 / 6.2 | 1.4 / 2.9 | 167 / 441 |
| 50 个 Run，各 1 个订阅者 | 1.7 / 2.9 | 1.0 / 43 | 173 / 1069 |

所有场景无丢失。`database` 的延迟由轮询间隔（`poll_min_ms` 250 到 `poll_max_ms` 1000，自适应）决定，不随订阅者数增长，因为同一进程同一 Run 共用一个轮询器。

### 生产者发布耗时

| 后端 | 每秒 | p50 | p99 |
| --- | --- | --- | --- |
| memory | 约 14 万 | <0.01 ms | 0.01 ms |
| redis | 约 4900 | 0.19 ms | 0.51 ms |
| database | 不适用（Run 自己的提交即发布） | | |

Redis 的每次发布是一次同步往返；一个 Run 的文本增量远低于每秒几千个，足够。

## 压测中发现并修复的问题

1. **memory 后端：先于首个事件连上的查看者要等到下一个心跳。** 订阅者只有在 Run 的日志已存在时才登记唤醒，日志在首次发布时才创建，所以提前连上的查看者要等心跳超时（默认 15 秒）才看到最前面的事件。现在订阅时创建日志；没有事件、没有等待者且超过保留期的空日志会被清理。回归测试：`test_memory_bus_wakes_a_subscriber_that_attached_before_the_first_event`。
2. **redis 后端：每个查看者各占一个阻塞 `XREAD` 和一条连接，与设计不符。** 设计与任务 2.3 写的是“每个进程每个 Run 一个读取器再扇出”，实现却是每个订阅者自己读。100 个订阅者时 p50 为 65.6 ms、p99 为 107 ms，现为 1.4 ms、2.9 ms；30 个查看者看 5 个 Run 时连接数从 31 降到读取器数加少量固定连接。晚加入的订阅者从流里补读它落后的部分，再接共享读取器，按事件 id 去重。
3. **共享读取器带来的新风险：一个读得慢的查看者会让它的队列无限增长。** 每个订阅者的队列上限 2048 个事件；超出就把它移出读取器并抛 `BusUnavailable`，订阅管线随即改读数据库直到 Run 结束，不影响其他查看者。
4. **新连上的查看者也会先发一次 `XRANGE` 做断档检查**，一批查看者同时连上会把连接池撑到查看者数。只有带游标续读的才需要这次检查，现已跳过新连接。

## 故障注入

`tests/test_run_events_faults.py` 对真实 `redis-server`（每个测试自启一个，可杀掉再启动）运行，没有 `redis-server` 时跳过。`fakeredis` 做不到杀进程与重启，所以这些用例单独成文件。

| 故障 | 期望与结果 |
| --- | --- |
| Redis 在发布中途被杀 | 第一次发布在 2 秒内失败，随后 47 次发布 0.5 秒内全部立即失败（熔断，不再逐次连网）；Run 不受影响。Redis 回来、熔断窗口过后恢复发布 |
| Redis 在查看者读取时被杀 | 查看者在有限重试后收到 `BusUnavailable`（订阅管线据此改读数据库并发 `stream.resync`）；Redis 以空数据重启后，新订阅者能收到后续事件 |
| 查看者断开（取消） | 30 个查看者看 5 个 Run 时恰有 5 个读取器；全部取消后读取器为 0，服务器连接数回到 3 以内 |
| 查看者卡住不读 | 其余查看者收到全部 300 个事件；卡住的那个被切断并收到 `BusUnavailable` |
| worker 消失 | 生产者租约过期后 `producer_state` 为 `expired`，原 worker 无法续租；接手的 worker 拿到新令牌，僵尸 worker 继续推文本被围栏拒绝（真实 Redis 上的 Lua） |
| Run 结束 | 结束标记到达所有查看者，流在保留期后被 Redis 删除 |

### 没有在这里覆盖的

- **整套 worker 进程被杀后的 Run 恢复**：属于租约与账本，已有 `test_worker_concurrency.py`、账本与未知结果的测试，这里只验证事件通道一侧。
- **database 后端的故障**：它不依赖额外服务，数据库不可用时整个平台不可用。
- **PostgreSQL 上的 database 后端延迟**：只在 SQLite 上测过。
