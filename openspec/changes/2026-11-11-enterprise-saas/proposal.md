# 企业级员工智能体平台（SaaS 多租户）

## 状态

草案第三版（2026-11-11，同日补充个人渠道）。按用户对第二版的答复调整：资源分为个人与企业两种归属，企业知识库可以指定知识库管理员；企微支持一个企业配置多个自建应用（工作台、管理后台、单个智能体）与扫码登录；保留 IM 渠道，每个渠道绑定一个智能体。同日补充：个人智能体可挂企微智能机器人（经审核，策略可调），并增加个人使用的微信、QQ 渠道。“需要你确认的项”已全部答复。用户 2026-11-11 确认后开始实施，进度与偏离见 `tasks.md`。

## 背景

现有底座里，运行时契约、ToolGateway 单调守卫、执行时复核授权、三类授权分离（ResourceGrant / ActionGrant / ActionApproval）、派发账本与审计都可以直接用于企业场景。偏 To C 的部分集中在“谁说了算”：

| 维度 | 现状（代码位置） | 企业场景的缺口 |
|---|---|---|
| 空间形态 | 自助注册可选个人空间或企业空间（`auth/accounts.py` `register`），登录默认进入个人空间 | 员工的内容和费用游离在企业之外 |
| 资源归属 | 智能体与知识库只有“创建者”这一种归属；空间 owner、admin 与创建者都能改；角色可以授予智能体的 `edit`、`publish`、`manage`（`agents/access.py`、`knowledge/access.py`） | 分不清“员工自己的”与“企业下发的”；企业下发的智能体可能被员工改动；企业知识库无法指定专人维护 |
| 私有内容 | **知识库对本空间全体成员可读**（`can_read`） | 企业内缺少“只有我能看”的知识库 |
| 企业微信 | 每个部署只有一个自建应用（`configs [wecom]`、`auth/wecom.py`），只做扫码登录与绑定，不自动开户，不同步通讯录 | 每家企业接入自己的企微，并且一个企微企业里可能有多个自建应用分别对应工作台、管理后台和单个智能体 |
| IM 渠道 | 前端有 WeKnora 的 IM 渠道面板（`components/IMChannelPanel.vue`，挂在智能体编辑器里），`connectors/wecom` 只有空包 | 需要让企微机器人等 IM 渠道绑定到单个智能体 |
| 组织与授权 | `org_units` 每企业一棵树，但组织位置不参与授权 | 智能体与知识库无法按部门开放 |
| 企业管控 | 没有企业级策略；企业空间内可用个人模型与个人 Key；共享空间可以跨企业共享 | 企业需要统一控制自建、模型、外部共享与数据留存 |
| 前端 | `apps/web` 是一个 Vite 应用（WeKnora 副本）；员工设置、空间管理与部署运维混在一起；保留了大量没有 Nexus 后端的 WeKnora 功能；本机 `pnpm build` 因内存不足失败 | 员工端与管理端分开、各自精简；员工端适配企微 H5 |
| 平台管理 | `/platform-admin` 与跨企业的 `/admin/*` 接口能看到所有企业的智能体与会话 | SaaS 下平台运维不应通过 Web 看到企业数据 |
| 成本 | 只有并发上限与后台模型限流 | 没有按企业、部门、个人的 Token 预算与用量报表 |
| 部署 | 默认 SQLite，PostgreSQL 目标环境验收（路线图 2.9）暂跳过 | SaaS 必须以 PostgreSQL 为事实源，多 worker 部署 |

## 已确认的方向（2026-11-11）

1. **SaaS 多租户，租户即企业**：所有数据按企业（`tenants.kind = 'enterprise'`）隔离；不引入部门工作区层级，部门差异通过组织驱动授权表达。只有正式企业，没有试用或套餐；自助注册即创建企业，注册人为 owner。
2. **取消独立个人空间，改为企业内的个人区**：现有个人空间数据在开发库中直接删除。
3. **资源分两种归属**：
   - **个人资源**：员工在工作台创建的智能体与知识库，由创建者本人维护。
   - **企业资源**：企业管理员在管理后台创建并分配给员工的智能体，只有企业管理员能维护；企业创建的知识库，可以指定**知识库管理员**维护内容。
4. **登录方式**：
   - 企微内的自建应用免登。一个企微企业可以配置多个自建应用，分别对应员工工作台、企业管理后台、单个智能体（一个智能体一个应用，打开即进入该智能体的对话），几种形式同时支持；
   - 企微扫码登录（电脑浏览器）。
5. **保留 IM 功能，每个 IM 渠道绑定一个智能体**：企业智能体用企微（智能机器人、自建应用消息）；个人智能体可以挂企微智能机器人，但须企业管理员审核后才能使用，并由企业策略开关控制；另增加微信与 QQ 渠道，方便员工个人使用自己的智能体。
6. **员工自建智能体默认开放**；个人模型默认关闭；企微自动开户的默认角色为 `contributor`。
7. **不做离职资产移交，不做审批路由**：离职只撤销企业成员身份；工具执行前的确认维持现状，由 Run 发起人本人确认。
8. **取消平台管理界面**：能按企业配置的并入企业管理后台；部署级配置只通过 `configs/nexus.toml` 与命令行管理；删除跨企业的清单接口。平台运营不考虑。
9. **删除没有 Nexus 后端的 WeKnora 功能**：助手、Ollama、WeKnora Cloud、CLI、Chrome 插件、Claw 技能等（清单见 `design.md` 4.5）。
10. **前端拆成三个 Node 项目**：基于 pnpm workspace，`core`（共用组件、状态、hooks、请求层）、员工工作台、企业管理后台。后端 API 保持一个服务。

## 决定

1. **租户形态**：只创建企业租户。自助注册时企业名称与编码选填，缺省自动生成。一个账号可以属于多家企业。迁移删除 `kind = 'personal'` 的租户及数据，`kind` 只保留 `enterprise` 与 `system`。
2. **资源归属与维护权**（智能体与知识库增加 `ownership`：`personal` 或 `enterprise`）：

   | | 个人资源 | 企业资源 |
   |---|---|---|
   | 在哪里创建 | 员工工作台 | 企业管理后台 |
   | 谁能创建 | 企业策略允许自建的成员 | 企业管理员（owner、admin，或持有 `enterprise_agents:manage` / `enterprise_kbs:manage` 的角色） |
   | 智能体的编辑、发布、停用、删除 | 创建者 | 企业管理员 |
   | 知识库的设置、可见范围、删除、共享 | 创建者 | 企业管理员 |
   | 知识库内容维护（文档、分块、问答） | 创建者 | 企业管理员与该库指定的**知识库管理员** |
   | 共享或分配给他人 | 创建者可共享，对方只获得“使用” | 企业管理员按角色、部门、成员分配，对方只获得“使用” |
   | 企业 owner、admin 的治理权 | 查看、停用、删除、转为企业资源 | 完全权限 |

   - 共享与分配只授予“使用”（查看与运行），不再授予编辑、发布、管理；现有角色授权中的 `edit`、`publish`、`manage` 在迁移时降为 `run`。
   - 依赖方向：个人智能体可以绑定自己的知识库和全企业可见的企业知识库；企业智能体只能绑定企业知识库，不能依赖个人资源。
   - “转为企业资源”由企业 owner、admin 执行，转换后归属改为 `enterprise`，原创建者失去维护权（如需继续维护知识库，可被指定为知识库管理员），写入审计。
   - 迁移：现有智能体与知识库一律设为 `enterprise`（开发库）。
3. **企业内的个人区**：知识库增加 `visibility`：`private`（个人知识库只有创建者可见；企业知识库只有企业管理员与知识库管理员可见）或 `tenant`（全企业成员可读）；E4 再增加按部门、成员开放。新建个人知识库默认 `private`。绑定的知识库可见范围必须覆盖智能体的使用范围，否则发布检查拦截。会话、记忆、产物沿用现有的本人隔离规则。
4. **企业策略（`enterprise_policies`）**：`self_build_agents`（`all` 默认、`org_units`、`none`）、`personal_models`（默认 `false`）、`external_sharing`（默认 `false`）、`personal_wecom_channels`（个人智能体的企微机器人：`review` 默认，须审核后启用；`open` 无需审核；`disabled` 不允许）、`personal_external_channels`（个人智能体能否挂微信、QQ，默认 `true`）、`retention_days`。只能收紧，不放宽平台已有的守卫。
5. **企业微信：企业、应用、登录**：
   - 每个 Nexus 企业绑定一个企微企业（`corp_id` 全局唯一），在其下登记任意多个自建应用，每个应用有一个**用途**：`workspace`（员工工作台）、`admin`（企业管理后台）、`agent`（单个智能体，必须指定一个可用的智能体，一个智能体最多对应一个应用）。同一用途可以登记多个应用（例如两个部门各有一个工作台应用）。
   - **企微内免登**：每个应用的主页地址为 `/wecom/apps/{app_id}/entry`，经企微网页授权取得成员身份后，按用途进入工作台、管理后台或该智能体的对话页。进入企业管理应用需要当前企业空间 owner 或管理员角色，进入智能体对话仍需该智能体的使用权；企微的可见范围只决定谁能看到应用，不替代 Nexus 的权限判断。
   - **企微扫码登录**：企业在应用中指定一个用于扫码登录的应用（默认是第一个 `workspace` 应用）；登录页按企业编码或扫码回调中的 `corp_id` 找到企业。
   - **自动开户**：已同步到本企业的成员，第一次经任一应用或扫码进入时，自动创建账号并加入企业（`contributor`），不设置本地密码。
   - **邮箱密码登录保留**：用于注册企业的 owner、没有接入企微的企业，以及企微不可用时的后备。
   - **通讯录同步**：每天全量一次，加上回调增量，同步部门、成员、主部门、在职状态。离职（删除或移出范围）时撤销企业成员身份，资产不动。
6. **IM 渠道**：每个渠道绑定一个智能体，在该智能体的“渠道”页配置；一个智能体可以有多个渠道。

   | 渠道 | 接入方式 | 谁能对话、以谁的身份运行 | 企业智能体 | 个人智能体 |
   |---|---|---|---|---|
   | 企微智能机器人 | 在企微中创建智能机器人（API 模式），把机器人 ID 与密钥填入渠道；长连接接收消息 | 企业成员单聊或群里 @；以发送者本人身份运行，须有该智能体的使用权 | 企业管理员配置，立即生效 | 由 `personal_wecom_channels` 决定：默认提交后进入“待审核”，企业管理员通过后才启用；管理员可随时停用 |
   | 企微自建应用消息 | `agent` 用途的自建应用（决定 5） | 同上 | 支持 | 不支持（自建应用由企业管理员登记） |
   | 微信 | 员工在渠道页用自己的微信扫码，绑定为该智能体的微信机器人（腾讯 iLink Bot 接口，长轮询收消息） | 只有绑定者本人；以绑定者身份运行 | 不支持 | 由 `personal_external_channels` 控制，默认允许，无需审核 |
   | QQ | 员工在渠道页用手机 QQ 扫码创建并绑定 QQ 官方机器人（或手动填入机器人 AppID 与密钥）；长连接收消息 | 只有绑定者本人（首次对话发送渠道页显示的绑定码完成认领）；以绑定者身份运行 | 不支持 | 同上 |

   - 企微渠道：发送者的企微身份映射为 Nexus 成员；找不到或已离职回复“未开通”，没有使用权回复“无权限”。会话按（渠道、会话、成员）隔离，群聊里每个人的对话互不混入。
   - 微信、QQ 渠道只服务绑定者本人：其他人发来的消息不处理；群聊消息不处理（首版只做私聊）。智能体被停用、删除，或绑定者离职时，渠道自动停用。
   - 需要人工确认的工具调用，回复“请到工作台确认”并附链接。
   - 对外嵌入页同样是“绑定一个智能体”的渠道（后端另提案）。

7. **组织驱动授权**：分配与共享的接收方从“角色”扩展为“角色、部门（含子树）、成员”。部门授权在每次判断时按当前组织关系展开。部门不继承空间角色。
8. **企业级管理角色**：内置 `security_admin`（工具风险策略、企业策略）与 `auditor`（只读审计，默认看不到正文）；新增 API 权限 `policy:manage`、`audit:read_content`、`enterprise_agents:manage`、`enterprise_kbs:manage`。
9. **前端：三个 Node 项目与功能精简**：`apps/web` 改为 pnpm workspace 根，下设 `core`、`workspace`、`enterprise`（结构见 `design.md` 第 4 节）。工作台适配桌面与手机，并包含“单智能体模式”页面（供 `agent` 用途的企微应用打开）与对外嵌入页入口；管理后台只做桌面。入口由 `/auth/me` 的 `entries` 决定。IM 渠道面板保留，挂在智能体的“渠道”页。
10. **取消平台管理界面**：删除 `/platform-admin`、跨企业的 `/api/v1/admin/*` 接口与 `configs [wecom]`；`users.is_platform_admin` 只保留给命令行与内置技能导入接口。企业配置的外部向量库与存储后端连接走模型调用同一套网络出口策略。
11. **SaaS 部署前提**：PostgreSQL 为事实源，`split` 模式加多 worker，Redis 事件通道；路线图 2.9 改为本提案的前置门禁。

## 范围

阶段划分见 `tasks.md`。每个阶段开始前，在 `design.md` 补齐该阶段的接口与表结构，并经用户确认。

- E0 资源归属与维护权：个人与企业两种归属、知识库管理员、共享只授予“使用”（决定 2）。
- E1 租户与个人区：注册即创建企业、删除个人空间、知识库可见范围、企业策略、企业级管理角色、删除跨企业接口、PostgreSQL 门禁（决定 1、3、4、8、10、11）。
- E2 前端重构：pnpm workspace 三项目、功能精简、员工工作台与企业管理后台（决定 9）。
- E3 企业微信：企业与多应用登记、企微内免登、扫码登录、自动开户、通讯录同步、离职撤销（决定 5）。
- E4 IM 渠道：渠道绑定智能体；企微智能机器人（含个人机器人审核）、自建应用消息、微信、QQ（决定 4、6）。
- E5 组织驱动授权：按部门、成员分配与共享（决定 7）。
- E6 成本与配额：企业、部门、个人三级 Token 预算与用量报表。
- E7 数据治理：留存清理、审计导出。

范围外：

- 平台运营界面（开通、停用、上限、计费）。
- 离职资产移交、审批路由。
- 对外嵌入页的后端实现（另提案）。
- 企微代开发应用与第三方应用、企微群机器人 Webhook（只能发不能收）、企业智能体的微信与 QQ 渠道（对外客服场景）、微信与 QQ 的群聊、飞书、钉钉、SAML、LDAP、SCIM。
- 知识库文档级 ACL 与源系统权限同步。

## 验收

- 自助注册创建企业；不存在个人空间；属于多家企业时可以切换。
- 员工在工作台创建的智能体与知识库为个人资源，只有本人能编辑；共享给他人后，对方只能使用。企业管理员在管理后台创建的智能体与知识库为企业资源，员工不能编辑；企业知识库指定的知识库管理员可以维护内容，不能修改设置、可见范围或删除。企业智能体不能绑定个人知识库。
- 同一企微企业登记了工作台、管理后台、单智能体三类应用后，从企微分别打开，依次进入工作台、企业管理应用（没有企业管理入口时被拒绝）、该智能体的对话页（无使用权时被拒绝）；电脑上扫码可以登录；已同步、首次进入的成员自动开户；离职同步后，该成员的下一次请求与工具调用都被拒绝。
- 企微智能机器人绑定一个智能体后，成员在单聊或群里 @ 机器人即可对话，以发送者本人身份运行；没有使用权的成员收到“无权限”；群里不同成员的对话互不混入。个人智能体的企微机器人在审核通过前不响应消息，策略改为 `disabled` 后已启用的也随之停用。
- 员工用自己的微信或 QQ 扫码绑定个人智能体后，可以在私聊中与之对话；其他人的消息不被处理；`personal_external_channels = false` 时不能绑定，已绑定的停用。

- `apps/web` 下 `pnpm build` 产出工作台与管理后台两份静态产物，工作台产物不含管理后台代码；`design.md` 4.5 列出的 WeKnora 功能已移除；`/platform-admin` 与跨企业接口已删除。

## E2.5.3 部门批量角色分配与授权校验修复（已确认）

下一批接入角色页的部门批量分配。核对发现 `tenants/membership.py::assign_role_to_unit` 仅调用要求 `members:manage` 的 `_manager`，未复用单成员角色分配的 `roles:manage` 与授予范围校验。因此，只有成员管理权限的操作者，可能通过部门批量接口分配自己未持有的高权限角色。该接口不能仅依靠前端候选过滤保护。

建议先补齐服务端校验：保留 `members:manage`，额外要求 `roles:manage`，目标角色的菜单/API 授权必须为操作者有效授权的子集，规则与单成员分配一致；拒绝时返回 403 且不得写入任何分配。路径、输入、成功响应和事务/审计结构保持现有契约。

随后在 `/admin/roles` 增加按部门路径选择、角色选择、范围提示、确认和结果反馈。只处理当前部门直接关联的活跃成员，不含下级；跳过 owner 与已分配成员。页面另需 `org:manage` 读取组织树，不允许手填部门 ID。不增加按部门持续继承、批量撤销、子树分配或后台新任务。

本批涉及服务端权限规则变化，用户已明确确认实施，任务仍归原变更 E2.5.3.5。

## E2.5.5 追加提案：企业成员临时停用与恢复（2026-11-15 已确认）

现有成员管理只支持永久移除，不能暂时阻止成员访问后再恢复。拟增加 `suspended` 成员状态与 `suspended_at` 时间，提供 `PATCH /api/v1/tenants/{tenant_id}/admin/members/{member_id}/status`（`active | suspended`）。停用即拒绝后续企业身份、资源访问与新 Run，但保留角色、部门关系、资源和历史；已开始的 Run 不自动取消，后续操作继续受执行时授权检查。恢复显式设回 active，不重置角色或部门关系。

状态写入要求 `members:manage`；owner 变更仍仅限 owner，并在租户事务锁内保护至少一名 active owner。永久移除仍写为 `revoked`。邀请或手工添加不得隐式恢复 suspended 成员；企微同步不得覆盖人工停用，确认离职仍按既有规则撤销。成员列表展示 active/suspended 并提供停用确认和恢复操作。完整需求与设计见 `specs/enterprise-member-status-administration/spec.md`、`design.md` E2.5.5。

用户已确认按此合同实施（2026-11-15）。实施状态及验收限制见 `tasks.md` E2.5.5。


## E2.5.8 追加提案：企微组织同步归属与只读保护（2026-11-15 已确认）

当前组织页仅在前端把 `source=wecom` 节点设为只读；通用 API 仍可修改/删除这些节点。手工创建的企业根节点可能同时映射企微顶级部门（`source=manual` 且有 `external_id`），成员归属记录也没有来源字段，因此企微下一次同步可能覆盖管理员操作，或清掉手工归属。拟在服务端按同步来源保护节点与成员关联，并在现有企微设置页清楚呈现同步状态。

方案草案见 `design.md` E2.5.8 和 `specs/enterprise-organization-sync-ownership/spec.md`：同步管理节点判定为 `source=wecom` 或具有企微 `external_id`；对名称、父级、启停、删除的手工写入返回冲突，允许在启用同步节点下创建手工子部门。树 DTO 增加 `sync_managed`，成员归属记录增加来源 `manual | wecom | mixed`，同步只撤销其来源贡献，手工移除只撤销手工贡献。历史归属保守回填，并对可由现有通讯录精确确认的企微关联建立同步来源。复用 `/admin/wecom` 的既有 `sync_status`、`sync_error`、`synced_at` 和立即同步接口；不增加调度开关、同步频率或通讯录范围配置。

用户已于 2026-11-15 确认按此合同继续实施，验证范围与限制见 tasks.md。
