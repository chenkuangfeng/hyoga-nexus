# 会话上下文缓存与 Run 装配

## 状态

待确认。确认前不编码。

## 原因与范围

当前 worker 每次执行 Run 都从数据库装配全部会话上下文（历史事件、工作检查点、智能体与模型版本、记忆快照等）。同一会话连续发消息时，每个 Run 都重复读取相同的历史，历史变长后这部分开销会持续增加。

本提案在 worker 进程内增加**会话数据缓存**，让同一会话的连续 Run 复用已装配的数据，只读取自上次以来新增的部分。

范围内：
- 会话数据缓存：历史投影、工作检查点、会话绑定的智能体版本与模型配置引用、记忆快照引用。
- Run 装配改为"命中则增量读取，未命中或不一致则全量读取"。

不在范围内：
- 缓存权限判断。授权仍在每次工具调用和资源读取时查询数据库。
- 缓存执行对象（如 `NativeEngine` 实例）。每个 Run 仍创建执行对象，执行完释放。
- 派发机制、单机 SQLite 与多租户 PG 的存储切换、Redis 的引入。这些另行提案。

## 变更

- 缓存为进程内、有界的结构（最多 N 个会话、单会话字节上限、空闲 TTL）。它**不是事实源**：进程重启后清空，不影响恢复。
- 每个会话在 PostgreSQL 中有一个单调递增的修订号，凡是影响提示词可见内容的写入（新事件、新消息、检查点更新、绑定变化）都增加它。
- Run 开始时：读取会话修订号（主键查询，代价很小）；与缓存一致则直接使用；修订号增加则只读取序号大于缓存水位的事件并增量投影；缓存缺失或数据异常则全量重建。
- 同一进程内的写入直接更新缓存；其他进程的写入由修订号检查发现，不依赖通知机制。
- 恢复规则不变：恢复前仍校验快照版本、会话、主体、智能体与模型版本、资源授权，缓存只提供数据，不替代这些校验。
